# ORB-SLAM3 — logic-error & optimization audit

> **Scope & method.** This is a *static* source audit of this ORB-SLAM3 V1.0 fork,
> cross-referenced against the primary literature (Campos et al. 2021; Forster et al.
> 2017; Mur-Artal & Tardós 2017; Rublee et al. 2011; Kannala–Brandt 2006; Urban et al.
> 2016; Horn 1987; Gálvez-López & Tardós 2012) and the upstream GitHub issue tracker.
> Findings were produced by a fan-out of per-subsystem reviewers, each finding was then
> put through an adversarial verification pass (correctness lens + literature lens), and
> a sample of the high-severity items was additionally hand-checked against the code.
> Of the verifications that completed, **28 confirmed / 5 plausible / 1 refuted**.
>
> A **curated batch of high-confidence fixes has been applied** on this branch
> (see "Already fixed" below); the remaining suggested fixes are *proposals*:
> ORB-SLAM3's behaviour is numerically sensitive, so review each against your own
> datasets before applying. Line numbers refer to this checkout. "Confidence" is
> the reviewer's, tempered by verification; treat `low`/`plausible` items as leads,
> not conclusions.

## Already fixed on this branch

- **`LoopClosing::mnFullBAIdx` declared `bool`, used as an integer counter/index.**
  `include/LoopClosing.h`. It is incremented in three places and read as
  `int idx = mnFullBAIdx; ... if(idx != mnFullBAIdx)` to detect whether a *newer*
  Full-BA was requested while a Global BA is running (so a stale GBA result is
  discarded). As a `bool` it saturates at `1` after the first increment, so the
  staleness check silently stops working after the first GBA. In ORB-SLAM2 this field
  is `int`. Fixed by typing it `int` (which also makes it C++17-legal — `bool operator++`
  was removed in C++17). *Reference: Mur-Artal & Tardós, "ORB-SLAM2", IEEE T-RO 33(5),
  2017, §V (loop closing / full BA); ORB-SLAM2 source `LoopClosing.h`.*

The following high-confidence fixes were also applied (each matches sibling code or
the upstream reference; the corresponding finding below has the full analysis):

- **`ORBmatcher.cc` `SearchByBoW` right-camera match** — removed the `|| true` that
  unconditionally bypassed the Lowe ratio test, restoring symmetry with the
  left-camera branch.
- **`MLPnPsolver.cc` RANSAC loop** — `||` → `&&` so a single `iterate()` respects its
  per-call budget instead of draining `mRansacMaxIts` (matches `Sim3Solver`/`PnPsolver`).
- **`MLPnPsolver.cc` iteration count** — `pow(ε,3)` → `pow(ε, mRansacMinSet)`; the MLPnP
  minimal sample is 6 points, not 3, so RANSAC no longer terminates far too early.
- **`Optimizer.cc` GBA stereo diagnostics** — `vpEdgeKFMono[i2]` → `vpEdgeKFStereo[i2]`
  in the stereo-edge loop (copy-paste index bug).
- **`Optimizer.cc` 4-DoF pose graph** — the essential-graph information matrix set
  `matLambda(0,0)` twice and never `(2,2)`; now sets `(2,2) = 1e3`.
- **`Tracking.cc` `Relocalization`** — free the per-candidate `MLPnPsolver`s on both
  return paths (they were leaked every relocalization attempt). This surfaced a
  latent upstream bug — **`MLPnPsolver::~MLPnPsolver()` was declared but never
  defined** — now given its (trivial) definition in `MLPnPsolver.cpp`.

The following crash / undefined-behaviour fixes were also applied (guards only — no
behaviour change on the happy path):

- **`ORBextractor.cc` `DistributeOctTree`** — clamp `nIni` to ≥1; portrait/tall
  regions gave `nIni == 0` and a divide-by-zero.
- **`ORBextractor.cc` cell grid** — clamp `nCols`/`nRows` to ≥1; the smallest pyramid
  levels gave 0 and a divide-by-zero in `ceil()`.
- **`MapPoint.cc` `EraseObservation`** — guard `mObservations.begin()` when the map
  became empty (was dereferencing `begin() == end()`).
- **`Tracking.cc` `PreintegrateIMU`** — the empty-queue and `n==0` early returns left
  `mCurrentFrame.mpImuPreintegrated` NULL, later dereferenced by the inertial pose
  optimizers (segfault, issue #730); now set to the KF-level preintegration.
- **`KeyFrame.cc` `ComputeSceneMedianDepth`** — read the locked snapshot instead of the
  live `mvpMapPoints` (TOCTOU NULL-deref) and guard the empty-vector unsigned underflow.

All of the above were verified to compile and link, and the ROS 2 node built on top
runs on Jazzy. The relocalization/matching changes **do** alter behaviour (for the
better, per the references) — validate on your datasets; the crash/UB fixes are
guards with no happy-path change.


## High severity

### 1. KeyFrame::ComputeSceneMedianDepth ignores its own locked snapshot and reads shared mvpMapPoints unlocked, causing a TOCTOU null-dereference / out-of-bounds

- **Location:** `src/KeyFrame.cc:795` — *thread-safety*, confidence high
- **Problem:** The function takes mMutexFeatures and copies the map-point vector into the local snapshot `vpMapPoints` (line 785) specifically to read it safely, but the loop at lines 794-802 then accesses the shared member `mvpMapPoints[i]` (both the null check at 795 and the deref at 797) with the lock already released at line 788. The snapshot vpMapPoints is dead code. This is a genuine data race with any thread calling KeyFrame::EraseMapPointMatch/AddMapPoint (which hold mMutexFeatures). Worse, it is a TOCTOU: between the `if(mvpMapPoints[i])` at line 795 and the `MapPoint* pMP = mvpMapPoints[i]` at line 797, a concurrent EraseMapPointMatch can set the slot to NULL, after which `pMP->GetWorldPos()` (line 798) dereferences NULL. Additionally, if the keyframe has N>0 but every slot is null, vDepths is empty and line 806 computes `vDepths[(vDepths.size()-1)/q]` with an unsigned underflow (0-1 -> SIZE_MAX), an out-of-bounds read.
- **Trigger:** Line 785 `vpMapPoints = mvpMapPoints;` under lock; lock scope ends line 788; loop lines 794-802 uses `mvpMapPoints[i]` not `vpMapPoints[i]`. Called from LocalMapping::InitializeIMU and Tracking initialization while local BA/MapPoint culling can run on other threads and null out entries via MapPoint::SetBadFlag -> KeyFrame::EraseMapPointMatch. Concurrent NULLing between lines 795 and 797 -> segfault at line 798.
- **Suggested fix:** Use the snapshot consistently: replace `mvpMapPoints[i]` on lines 795-797 with `vpMapPoints[i]`, and guard line 806 with `if(vDepths.empty()) return -1.0;` before indexing.
- **Reference:** The concurrency model (Tracking, Local Mapping, Loop Closing threads sharing the map, all mutating keyframe map-point associations) is defined in Mur-Artal & Tardos, 'ORB-SLAM2,' IEEE T-RO 33(5), 2017, Sec. III. The dead-snapshot pattern is inherited from upstream ORB_SLAM2 KeyFrame::ComputeSceneMedianDepth (https://github.com/raulmur/ORB_SLAM2/blob/master/src/KeyFrame.cc), which likewise copies vpMapPoints then reads mvpMapPoints.

### 2. DetectCommonRegionsFromBoW passes member mbFixScale to OptimizeSim3 instead of the locally computed bFixedScale, wrongly fixing scale for monocular-inertial place recognition before inertial BA2

- **Location:** `src/LoopClosing.cc:767` — *logic-error*, confidence high
- **Problem:** Lines 763-765 compute a local override `bool bFixedScale = mbFixScale; if(mSensor==IMU_MONOCULAR && !GetIniertialBA2()) bFixedScale=false;` precisely so that the 7-DoF Sim3 optimization of a loop/merge candidate estimates scale while a monocular-inertial map is still scale-ambiguous. But the very next call (line 767) passes `mbFixScale` (the member), not `bFixedScale`, to Optimizer::OptimizeSim3(...,const bool bFixScale,...). For IMU_MONOCULAR, LoopClosing is constructed with bFixScale=true (System.cc:213 passes mSensor!=MONOCULAR), so mbFixScale==true. Thus for a monocular-inertial map that has not yet completed the second inertial BA, the Sim3 refinement freezes scale at 1.0 even though the map's metric scale has not been reliably recovered yet. The sibling code paths all use the corrected variable: DetectAndReffineSim3FromLastKF (line 556) and CorrectLoop (lines 1164-1167,1183) both pass the computed bFixedScale to OptimizeSim3/OptimizeEssentialGraph, confirming line 767 is a copy-paste defect, not intended behavior.
- **Trigger:** src/LoopClosing.cc:763-767. Trigger: IMU_MONOCULAR session, a loop/merge BoW candidate is geometrically validated while the current map has isImuInitialized() but !GetIniertialBA2() (i.e. before the ~10-15s full inertial BA). OptimizeSim3 is then forced with bFixScale=true; the wrong scale factor is baked into gScm/gScw and propagated into mg2oLoopSlw/mg2oMergeSlw and the essential-graph optimization, biasing the correction. Confirmed present in UZ-SLAMLab/ORB_SLAM3 master.
- **Suggested fix:** Pass the local override: `Optimizer::OptimizeSim3(mpCurrentKF, pKFi, vpMatchedMP, gScm, 10, bFixedScale, mHessian7x7, true);` (matching lines 556 and 1183).
- **Reference:** C. Campos, R. Elvira, J. J. G. Rodríguez, J. M. M. Montiel, J. D. Tardós, "ORB-SLAM3: An Accurate Open-Source Library for Visual, Visual–Inertial, and Multimap SLAM," IEEE Transactions on Robotics 37(6):1874-1890, 2021 — Sec. V (visual-inertial initialization: scale is a free optimization variable and is only well-determined after the map-refinement/second inertial BA, tracked by GetIniertialBA2()); Sec. VII (place recognition, Sim3/SE3 alignment). The code's own IMU_MONOCULAR carve-outs at lines 553-556 and 1166-1167 encode this requirement.

### 3. MLPnPsolver::iterate loop uses '||' instead of '&&', so a single iterate(5) call consumes the entire RANSAC budget and defeats the round-robin over relocalization candidates

- **Location:** `src/MLPnPsolver.cpp:115` — *logic-error*, confidence high
- **Problem:** The RANSAC loop is `while(mnIterations<mRansacMaxIts || nCurrentIterations<nIterations)`. With OR, the loop only stops when BOTH mnIterations>=mRansacMaxIts AND nCurrentIterations>=nIterations. Because every pass increments both counters and mRansacMaxIts (up to 300, or ~34 after the exponent-bug computation) is normally far larger than the per-call budget nIterations, the very first call runs the whole global iteration budget instead of the requested nIterations. The sibling solvers Sim3Solver::iterate (this same file-set, Sim3Solver.cc:167 and :240) and the ancestor ORB_SLAM2 PnPsolver::iterate both use '&&'. Relocalization (Tracking.cc:3681-3701) is explicitly written as an interleaved round-robin: it constructs one MLPnPsolver per candidate keyframe and calls pSolver->iterate(5,...) on each in turn so that all candidates get a fair share of iterations before any is abandoned. The '||' breaks this: the first candidate hogs the full budget in its first iterate() call, and mnIterations>=mRansacMaxIts then makes bNoMore=true so subsequent candidates that could have produced a valid pose are cut short or evaluated with the discard flag already set.
- **Trigger:** Tracking.cc:3683 calls `pSolver->iterate(5,bNoMore,vbInliers,nInliers,eigTcw)` inside a for-loop over candidate KFs (i=0..nKFs). With line 115 using '||', nCurrentIterations<5 stops mattering as soon as mnIterations<mRansacMaxIts is still true, so the loop body executes mRansacMaxIts times on the first candidate. Sim3Solver.cc:167 shows the intended form `while(mnIterations<mRansacMaxIts && nCurrentIterations<nIterations)`.
- **Suggested fix:** Change the operator from '||' to '&&' at line 115 to match Sim3Solver and PnPsolver, so each iterate() call performs at most nIterations passes and the global cap mRansacMaxIts bounds the total across calls.
- **Reference:** Deviation from ORB_SLAM3 Sim3Solver::iterate (src/Sim3Solver.cc lines 167, 240, same repository) and raulmur/ORB_SLAM2 PnPsolver::iterate (https://github.com/raulmur/ORB_SLAM2/blob/master/src/PnPsolver.cc, which uses `while(mnIterations<mRansacMaxIts && nCurrentIterations<nIterations)`). Fischler & Bolles, 'Random Sample Consensus', Comm. ACM 24(6), 1981 (round-robin/adaptive RANSAC budgeting).

### 4. MLPnP RANSAC iteration count is computed with pow(epsilon,3), but the MLPnP minimal sample is 6 points, so RANSAC terminates far too early

- **Location:** `src/MLPnPsolver.cpp:253` — *logic-error*, confidence high
- **Problem:** SetRansacParameters computes `nIterations = ceil(log(1-mRansacProb)/log(1-pow(mRansacEpsilon,3)))`. The exponent must equal the minimal-sample size s used by the estimator. MLPnP samples mRansacMinSet points, whose default is 6 (MLPnPsolver.h:67) and which Tracking.cc:3657 also sets to 6; computePose even asserts numberCorrespondences>5. The hard-coded exponent 3 is copied from Sim3Solver (Sim3Solver.cc:142), whose minimal set genuinely is 3, but was not updated for MLPnP's 6-point sample. Using s=3 instead of s=6 grossly underestimates the number of iterations needed for the target success probability, so mRansacMaxIts is clamped to a value roughly an order of magnitude too small and RANSAC stops before it has a reasonable chance of drawing an all-inlier 6-point sample, causing relocalization to fail at moderate outlier ratios.
- **Trigger:** With mRansacProb=0.99 and an inlier ratio w=0.5, the correct 6-point count is log(0.01)/log(1-0.5^6) = -4.605/log(0.984375) ≈ 292 iterations, whereas pow(w,3) gives log(0.01)/log(1-0.125) = -4.605/log(0.875) ≈ 34. mRansacMaxIts = max(1,min(nIterations,mRansacMaxIts)) is then clamped to ~34 instead of ~292, an ~8.6x shortfall; at w=0.4 the gap is far larger. minSet=6 confirmed at MLPnPsolver.h:67 and Tracking.cc:3657; sampling of mRansacMinSet points at MLPnPsolver.cpp:128.
- **Suggested fix:** Replace pow(mRansacEpsilon,3) with pow(mRansacEpsilon, mRansacMinSet) (i.e. exponent 6 for the default) at line 253 so the iteration budget matches the 6-point minimal sample.
- **Reference:** S. Urban, J. Leitloff, S. Hinz, 'MLPnP - A Real-Time Maximum Likelihood Solution to the Perspective-n-Point Problem', ISPRS Annals III-3, 2016 (minimal solver requires 6 correspondences). Standard adaptive-RANSAC iteration formula N=log(1-p)/log(1-w^s) with s the sample size: Fischler & Bolles, Comm. ACM 24(6), 1981; Hartley & Zisserman, 'Multiple View Geometry', 2nd ed., 2004, Alg. 4.5 (Table 4.3).

### 5. MapPoint::EraseObservation dereferences mObservations.begin() on an empty map when the erased KF was the point's only observation (use-after-erase UB)

- **Location:** `src/MapPoint.cc:191` — *logic-error*, confidence high
- **Problem:** In EraseObservation, after `mObservations.erase(pKF)` (line 188), the code does `if(mpRefKF==pKF) mpRefKF=mObservations.begin()->first;` (lines 190-191) without checking that mObservations is still non-empty. If pKF was the sole observing keyframe, the map is now empty, so begin()==end() and `->first` dereferences the past-the-end iterator — undefined behavior. mpRefKF is then set to garbage and is subsequently dereferenced by UpdateNormalAndDepth (line 468 `pRefKF->GetCameraCenter()`) and ComputeDistinctiveDescriptors, typically producing a segfault. The nObs<=2 -> SetBadFlag guard at lines 194-200 runs AFTER the bad assignment, so it cannot prevent it.
- **Trigger:** Reachable state: a stereo/RGB-D MapPoint observed in exactly ONE keyframe has nObs=2 (AddObservation lines 162-163 add 2 for a stereo obs) and a single entry in mObservations that is also mpRefKF. When that keyframe is culled, KeyFrame::SetBadFlag -> MapPoint::EraseObservation(pKF) erases the only entry, mObservations becomes empty, mpRefKF==pKF is true, and mObservations.begin()->first is dereferenced past the end. Same reachable for a monocular point whose observations were already thinned to the single ref KF by earlier erasures.
- **Suggested fix:** Guard the reassignment: `if(mpRefKF==pKF) mpRefKF = mObservations.empty() ? static_cast<KeyFrame*>(NULL) : mObservations.begin()->first;` and ensure all consumers of mpRefKF (UpdateNormalAndDepth line 468, ComputeDistinctiveDescriptors) null-check it. Ideally trigger SetBadFlag before touching mpRefKF when the map is empty.
- **Reference:** Identical unchecked pattern exists upstream: raulmur/ORB_SLAM2 src/MapPoint.cc EraseObservation (https://github.com/raulmur/ORB_SLAM2/blob/master/src/MapPoint.cc). The three-thread shared-map culling architecture that triggers this is described in R. Mur-Artal & J. D. Tardos, 'ORB-SLAM2: an Open-Source SLAM System for Monocular, Stereo, and RGB-D Cameras,' IEEE Trans. Robotics 33(5):1255-1262, 2017 (Sec. III, LOCAL MAPPING / Local Keyframe Culling). Related upstream crash reports: raulmur/ORB_SLAM2 issues #123 and #341.

### 6. DistributeOctTree divides by nIni=0 (crash) for portrait / tall images

- **Location:** `src/ORBextractor.cc:559` — *logic-error*, confidence high
- **Problem:** The initial number of octree root cells is nIni = round((maxX-minX)/(maxY-minY)) (line 559). This is the image width/height aspect ratio of the pyramid level rounded to an integer. For any image whose usable width-to-height ratio is < 0.5 (portrait / tall sensors, or level-0 crops with height > ~2x width), round() yields 0. The very next line hX = (maxX-minX)/nIni (line 561) then divides by zero, and vpIniNodes.resize(nIni) (line 566) allocates an empty vector that is immediately indexed at vpIniNodes[kp.pt.x/hX] (line 585) with hX = +inf/NaN. Result: NaN index into a zero-length vector -> out-of-bounds dereference / segfault. Even for ratios in [0.5,1.5) nIni collapses to 1, silently degrading the horizontal homogenization the octree is meant to provide (the whole level starts as a single tall root cell instead of a grid of ~square cells), which biases keypoint selection.
- **Trigger:** Trigger: run the extractor on a level whose (maxBorderX-minBorderX)/(maxBorderY-minBorderY) < 0.5, e.g. a 480x1080 portrait stream, or any camera rotated to portrait. Line 559 nIni=round(480/1080)=round(0.44)=0; line 561 hX=480/0 -> inf; line 566 vpIniNodes has size 0; line 585 vpIniNodes[kp.pt.x/inf]=vpIniNodes[0] indexes an empty vector -> UB/crash. There is no guard that nIni>=1.
- **Suggested fix:** Clamp the root-cell count: const int nIni = std::max(1, (int)round((float)(maxX-minX)/(maxY-minY))); (and symmetrically consider (maxY-minY)/(maxX-minX) roots when the image is taller than wide) so hX is finite and vpIniNodes is non-empty for any aspect ratio.
- **Reference:** raulmur/ORB_SLAM2 GitHub issue 'ORB extraction' https://github.com/raulmur/ORB_SLAM2/issues/283 (documents crash in DistributeOctTree when image width < height). Homogenization scheme described in R. Mur-Artal, J.M.M. Montiel, J.D. Tardos, 'ORB-SLAM: A Versatile and Accurate Monocular SLAM System,' IEEE Trans. Robotics 31(5), 2015, Sec. V-A.

### 7. Merge LocalBundleAdjustment calls GetMapPoint(-1) / mvKeysUn[-1] for right-only fisheye observations

- **Location:** `src/Optimizer.cc:3647` — *correctness-risk*, confidence high
- **Problem:** The second LocalBundleAdjustment overload (used by map merging, Optimizer::LocalBundleAdjustment(KeyFrame* pMainKF, ...)) filters observations with `!pKF->GetMapPoint(get<0>(mit->second))` at line 3647 and then reads `pKF->mvKeysUn[get<0>(mit->second)]` at line 3652 and `pKF->mvuRight[get<0>(mit->second)]` at 3654/3686, again with no `leftIndex != -1` guard. For a fisheye keyframe with a right-only observation (get<0>==-1), `GetMapPoint(-1)` indexes `mvpMapPoints[-1]` and `mvKeysUn[-1]` indexes out of bounds — undefined behavior during the visual welding BA of a non-inertial merge. Like MergeInertialBA it also never emits the right-camera edges, dropping those constraints.
- **Trigger:** Same root cause as the MergeInertialBA finding: src/MapPoint.cc:150-158 leaves get<0>==-1 for right-only fisheye observations. Path: LoopClosing merge (non-inertial) -> Optimizer::LocalBundleAdjustment(pMainKF, vpAdjustKF, vpFixedKF, pbStopFlag). Any observation on an adjust/fixed KF with left index -1 hits GetMapPoint(-1) at line 3647.
- **Suggested fix:** Extract `const int leftIndex = get<0>(mit->second);`, skip when leftIndex==-1 before calling GetMapPoint/indexing mvKeysUn/mvuRight, and add an explicit mpCamera2 right-observation branch as done in the tracking-side LocalBundleAdjustment.
- **Reference:** Campos et al., "ORB-SLAM3," IEEE T-RO 37(6), 2021, Sec. IV (fisheye tuple observations) and Sec. VII (map merging welding BA). Contrast with the guarded LocalBundleAdjustment overload at src/Optimizer.cc:1305 in the same file.

### 8. MergeInertialBA indexes mvKeysUn/mvuRight with get<0>(obs)==-1 for right-only fisheye observations, causing out-of-bounds access

- **Location:** `src/Optimizer.cc:4320` — *correctness-risk*, confidence high
- **Problem:** In the visual-edge construction loop of MergeInertialBA the observation index is taken as `get<0>(mit->second)` and used unconditionally to index `pKFi->mvKeysUn[...]` (line 4320) and `pKFi->mvuRight[...]` (line 4322/4344) without first checking that the left index is != -1. For the two-camera (KannalaBrandt8 fisheye stereo) rig, MapPoint::AddObservation stores the tuple as (leftIdx, rightIdx) and leaves get<0> == -1 whenever a feature is observed ONLY in the right image (idx >= NLeft). Every other BA in this file (e.g. LocalBundleAdjustment line 1305, FullInertialBA line 627) explicitly guards these accesses with `leftIndex != -1`; MergeInertialBA does not. When a windowed keyframe holds a right-only observation of a local map point, `mvKeysUn[-1]` / `mvuRight[-1]` is an out-of-bounds std::vector read (undefined behavior, typically a crash or corrupt keypoint). As a secondary defect, the function never adds the right-camera (mpCamera2) reprojection edges at all, so even when it does not crash it silently drops all right-fisheye constraints during an inertial map merge.
- **Trigger:** Trigger: stereo-fisheye + IMU configuration (e.g. TUM-VI), two inertial maps merged via LoopClosing -> Optimizer::MergeInertialBA. Any local MapPoint that has an observation with get<0>==-1 (right-only) on a keyframe inside the optimization window reaches line 4320 with index -1. Confirmed in src/MapPoint.cc:150-158: for NLeft!=-1 and idx>=NLeft only get<1> is set, get<0> stays -1. Contrast with src/Optimizer.cc:1305 which guards the identical access with `leftIndex != -1`.
- **Suggested fix:** Mirror the guarded pattern used elsewhere: compute `const int leftIndex = get<0>(mit->second);` and only build the mono/stereo left edge when `leftIndex != -1`, indexing mvKeysUn/mvuRight with leftIndex; add a separate `if(pKFi->mpCamera2){ int rightIndex = get<1>(mit->second); if(rightIndex!=-1){ ... EdgeMono(1) with mvKeysRight[rightIndex-NLeft] ... } }` block as in FullInertialBA.
- **Reference:** C. Campos, R. Elvira, J. J. G. Rodríguez, J. M. M. Montiel, J. D. Tardós, "ORB-SLAM3: An Accurate Open-Source Library for Visual, Visual–Inertial, and Multimap SLAM," IEEE Transactions on Robotics, vol. 37, no. 6, 2021 — Sec. IV (fisheye two-camera observation model, tuple observation indices) and Sec. VII (Map Merging / welding BA). Corroborated by the guarded counterpart in the same source file, src/Optimizer.cc:1305 (LocalBundleAdjustment) and :627 (FullInertialBA).

### 9. PreintegrateIMU early-returns leave mCurrentFrame.mpImuPreintegrated / mpImuPreintegratedFrame NULL, causing a NULL-dereference crash in IMU pose prediction/optimization

- **Location:** `src/Tracking.cc:1677` — *logic-error*, confidence high
- **Problem:** PreintegrateIMU() has two early-return paths that abort integration WITHOUT ever assigning mCurrentFrame.mpImuPreintegrated and mCurrentFrame.mpImuPreintegratedFrame: the empty-queue branch (lines 1636-1641) and the n==0 branch (lines 1677-1681, which also fails to call setIntegrated()). Only the normal path at lines 1728-1732 sets these pointers. A Frame is constructed with mpImuPreintegrated(NULL) and mpImuPreintegratedFrame(NULL) (Frame.cc:103), so after an early return these members stay NULL while the rest of Tracking proceeds as if IMU data were available. Downstream consumers dereference them with no NULL guard: PredictStateIMU() reads mCurrentFrame.mpImuPreintegratedFrame->dT at Tracking.cc:1770, and TrackLocalMap() (once the map's IMU is initialized) calls Optimizer::PoseInertialOptimizationLastKeyFrame/LastFrame, which do `new EdgeInertial(pFrame->mpImuPreintegrated)` and `pFrame->mpImuPreintegrated->C.block<3,3>(9,9)` (Optimizer.cc:4672, 4685) with no NULL check. Result is a segmentation fault, matching the reported crash cascade.
- **Trigger:** Trigger: any IMU_MONOCULAR/IMU_STEREO/IMU_RGBD run where a camera frame arrives with 0 or 1 usable IMU samples in the (prevFrame, curFrame] window — e.g. IMU rate close to camera rate, a dropped IMU packet, or a camera/IMU timeshift (Kalibr t_imu=t_cam-0.06s as in issue #730). The drain loop (1643-1675) leaves <=1 element, so `n = mvImuFromLastFrame.size()-1 == 0`, the function prints 'Empty IMU measurements vector!!!' and returns at 1680, leaving mCurrentFrame.mpImuPreintegrated==NULL. On the next optimization step this NULL is dereferenced. The sibling branches at 1630 and 1639 DO call setIntegrated() but STILL never set mpImuPreintegrated, so the state is inconsistent across all three exits.
- **Suggested fix:** In both early-return branches (and the n==0 branch) set mCurrentFrame.mpImuPreintegrated = mpImuPreintegratedFromLastKF, allocate/assign a (possibly empty) mpImuPreintegratedFrame, set mpLastKeyFrame, and call setIntegrated() before returning; alternatively add NULL guards in PredictStateIMU (1770) and the PoseInertialOptimization* entry points so a missing preintegration falls back to the visual model instead of dereferencing NULL.
- **Reference:** UZ-SLAMLab/ORB_SLAM3 GitHub Issue #730 'Empty IMU measurements vector!!! Not preintegrated measurement' (https://github.com/UZ-SLAMLab/ORB_SLAM3/issues/730), which reports the exact 'Empty IMU measurements vector!!!' log followed by 'Fail to track local map!' and a segmentation fault. Cross-ref C. Campos et al., 'ORB-SLAM3', IEEE T-RO 37(6), 2021, Sec. IV (IMU preintegration per Forster et al., 'On-Manifold Preintegration', IEEE T-RO 33(1), 2017) — every frame between two keyframes must carry a valid preintegration object for the inertial-only pose factor.

### 10. Double-precision KannalaBrandt8::project(Vector3d) computes theta/psi with single-precision atan2f/sqrtf, contradicting the double-precision analytic Jacobian used in the same g2o edges

### 36. compareNodes tie-break ignores UL.y, leaving octree expansion order platform-dependent (non-reproducible maps)

- **Location:** `src/ORBextractor.cc:538` — *portability*, confidence medium
- **Problem:** compareNodes (lines 538-553) orders nodes by (key-count, UL.x) only. Two sibling octree cells stacked vertically share the same UL.x and can hold the same number of keypoints, so compareNodes returns false for both (a,b) and (b,a): they are order-equivalent. In the refinement loop (lines 700-748) the sorted list is expanded largest-first and the loop breaks the instant lNodes.size()>=N (line 746). Which of two fully-tied nodes is expanded last, right at the N boundary, therefore decides which keypoints survive - and std::sort leaves the relative order of equivalent elements unspecified, so it can differ across STL/compiler versions. The result is that the exact retained keypoint set (hence descriptors, matches, and downstream trajectory) is not guaranteed reproducible across platforms even for identical input. compareNodes was introduced precisely to make DistributeOctTree deterministic, but the tie-break is incomplete.
- **Trigger:** Two cells N_a (UL=(x0,y0)) and N_b (UL=(x0,y1)) with equal vKeys.size() and equal UL.x: compareNodes(N_a,N_b) evaluates first==first -> falls to e1.second->UL.x < e2.second->UL.x -> x0<x0 is false -> returns false; compareNodes(N_b,N_a) also false. std::sort's output order for the pair is implementation-defined; when the loop hits lNodes.size()>=N between them, one node's best keypoint is kept and the other's dropped, flipping with the platform.
- **Suggested fix:** Make the comparator a strict weak ordering with a full tie-break, e.g. after comparing UL.x, compare UL.y (and finally the node's stored insertion index) so equal-size, equal-x nodes have a deterministic, platform-independent order.
- **Reference:** Reproducibility concerns with ORB_SLAM octree distribution, cf. raulmur/ORB_SLAM2 issue 'different results when running the project more than once' https://github.com/raulmur/ORB_SLAM2/issues/45 . Determinism requirement of the octree homogenization: R. Mur-Artal et al., IEEE T-RO 31(5), 2015, Sec. V-A.

### 37. Asymmetric last-cell skip thresholds (maxBorderX-6 vs maxBorderY-3) give anisotropic border coverage

- **Location:** `src/ORBextractor.cc:819` — *correctness-risk*, confidence medium
- **Problem:** Cells overlap symmetrically by 6 px on both axes (maxY = iniY+hCell+6 line 808, maxX = iniX+wCell+6 line 818). Yet the guard that drops a too-thin trailing cell uses different margins per axis: rows skip only when iniY>=maxBorderY-3 (line 810) but columns skip when iniX>=maxBorderX-6 (line 819). Because the geometry is symmetric, the correct threshold should be identical on both axes. As written, a thin trailing ROW spanning the last ~3-6 px is still processed (FAST run on a clamped strip), while the analogous thin trailing COLUMN is discarded. Near the bottom edge features can be extracted from a sliver that is refused near the right edge, producing an axis-dependent asymmetry in feature coverage at the image border.
- **Trigger:** Pick a level where the last column starts with iniX in [maxBorderX-6, maxBorderX-3): line 819 triggers 'continue' and that column is skipped. A row starting at the mirror position iniY in [maxBorderY-6, maxBorderY-3) does NOT satisfy line 810's iniY>=maxBorderY-3 and IS processed (maxY clamped at line 813). Same geometry, opposite outcome.
- **Suggested fix:** Use the same margin on both axes (both -3, matching the per-side FAST margin of 3 px): change line 819 to if(iniX>=maxBorderX-3) continue; so trailing rows and columns are treated identically.
- **Reference:** ORB-SLAM octree/grid extraction, R. Mur-Artal et al., IEEE T-RO 31(5), 2015, Sec. V-A (uniform feature distribution over the image). Long-standing inherited from raulmur/ORB_SLAM2 ORBextractor.cc.

### 41. Sim3Solver::ComputeSim3 divides by the imaginary-part norm of the quaternion, producing a NaN rotation when the minimal sample implies (near-)identity rotation

- **Location:** `src/Sim3Solver.cc:367` — *numerical*, confidence medium
- **Problem:** After extracting the eigenvector of N for the largest eigenvalue, the code forms the angle-axis vector as `vec = 2*ang*vec/vec.norm()` where vec is the imaginary part (sin(theta/2)*axis) of the unit quaternion and ang=atan2(vec.norm(), real). If the optimal rotation between the 3 sampled point pairs is (near-)identity, the quaternion is approximately [1,0,0,0], vec.norm() -> 0, and the division yields NaN, so mR12i = SO3f::exp(NaN) is NaN. The result is not a crash but a silently poisoned hypothesis: mT12i/mT21i become NaN, Project produces NaN reprojections, CheckInliers counts 0 inliers, and the RANSAC iteration is wasted. It is triggered whenever a minimal 3-pair sample corresponds to pure/near-pure translation with negligible relative rotation between the two keyframes' local frames.
- **Trigger:** Line 365 `double ang=atan2(vec.norm(),evec(0,maxIndex));` then line 367 `vec = 2*ang*vec/vec.norm();`. When vec.norm()==0 (identity rotation), this is 0/0. No guard precedes the division, unlike rodrigues2rot in MLPnPsolver.cpp:670 which checks omega_norm>epsilon.
- **Suggested fix:** Guard the normalization: if vec.norm() is below a small epsilon, set mR12i to the identity (theta≈0), otherwise proceed with vec = 2*ang*vec/vec.norm().
- **Reference:** B.K.P. Horn, 'Closed-form solution of absolute orientation using unit quaternions', JOSA A 4(4), 1987, Sec. 3-4 (the eigenvector of N is the unit quaternion; identity rotation gives a purely real quaternion). Standard quaternion-to-axis-angle numerical guard for small imaginary part.
